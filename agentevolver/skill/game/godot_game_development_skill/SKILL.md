# Godot game development

Respect the user's execution constraints. When they ask for source/design only or
defer testing, author the files and pending check plan without starting the engine,
tests or installers. The workflow below applies when execution is authorized.

This demo mounts only godot_environment. Use Bash for file operations and bounded
foreground commands. GameBuilder prepares the base authoring container before its
first turn. Both containers share canonical workspace paths; session plan/log/extension
paths are also available in the base. Use doctor to verify the Godot container, then
open_project and import_project. Missing images or rendering/input failures block play.
Do not invent actions or silently add a browser/background-job dependency.

## Choose a deliverable and keep it honest

Read the declared milestone. Maintain the complete campaign bible and a content
ledger with `planned / authored / implemented / played / blocked` states. A playable
slice can prove the production pipeline; it is not a complete long game. Never add
empty map gates, an hour estimate or autogenerated quest text to imply finished content.
Prioritize a complete exploration → creature interaction → battle → consequence →
save/reload loop. Expand chapters only after this loop and its visual presentation are coherent.

## Art direction and downloadable assets

Before producing the first region or creature roster, read
[the asset library and acquisition guide](references/asset-library.md). It contains
specific official packs, format/licensing notes and a base-container download recipe.
Use the absolute reference path supplied when this skill is invoked; references are
available through Bash in the mounted framework. Read this guide on demand rather
than copying the catalog into plan.md or the live Brief.

Use this skill's standard-library CLI through Bash for discovery and acquisition:

```bash
python scripts/assets.py search "forest" --provider all --godot 4.7 --limit 5
python scripts/assets.py info catalog:kaykit-forest --godot 4.7
python scripts/assets.py download catalog:kaykit-forest --out asset_sources --extract
```

The skill loader expands `python scripts/` to the mounted skill's absolute path.
Run from the canonical workspace; `asset_sources` belongs outside the game source.
`search` supports a curated bilingual catalog, the new Godot Store API and legacy
AssetLib API. Use English keywords for remote providers. `info` returns file/release
keys; supply `download --file KEY` when multiple are available. JSON output includes
errors/partial results and the script exits nonzero on failure. Read the full command
and provider contracts in [the CLI guide](references/assets-cli.md).

Download only needed resources, then read the returned manifest/license and inspect
selected files before importing. The CLI stages archives and can extract them; it never
installs/enables an addon, executes downloaded code or modifies project.godot. Reconcile
code addons and native extensions with the actual engine/renderer before activating.

Choose one visual direction in the detailed plan: palette, character proportions,
material treatment, camera framing, lighting, environment density, typography and UI.
Select a compatible family of assets for creatures, people, vegetation, buildings and
interface. Download the needed free packs through base Bash, retain their provenance,
and import selected resources through Godot. Do not assume curl, git, Blender or a
browser exists; Python urllib and zipfile are available in the default base. Downloads
are ordinary development work when execution is authorized, subject to user constraints.

For Tidebound Echoes, begin with a warm, stylized island-adventure direction: expressive
animated companions, a layered coastal village, readable paths and restrained ocean/sky
colors. Evaluate Quaternius Cute Animated Monsters for companions, its character and
village packs for people/buildings, and Kenney Nature Kit and UI Pack for compatible
support. These are candidates; inspect the actual imported result before committing to
the combination. Adapt art to original species and story roles; retain source authorship.

Make one small representative scene before mass-producing maps: an arrival view, player
and companion, a few buildings/vegetation props, dialogue UI and one battle presentation.
When execution is allowed, inspect native screenshots at the intended play resolution
and animate/move the characters. Compare against the chosen direction, fix scale,
material, lighting, composition and UI conflicts, and record unresolved visual defects.
Asset download/import success and pixel-brightness checks do not establish visual quality.

Primitive meshes are useful for collision and temporary blockout. Mark visible placeholders
as pending replacement; do not build the delivered cast from labeled capsules or repeated
primitive bodies merely because they are fast to generate. Deliberate procedural art is
acceptable when it meets the same visual criteria. If a download is blocked, record why
and try a compatible catalog alternative; do not silently lower the presentation target.
Keep visual acceptance pending when rendering is deferred. No automatic user approval
gate is added: perform this self-review within the authorized development work.

Use [the presentation review procedure](references/presentation-review.md) to turn this
into an actual work sequence and persist current visual evidence. This applies to inherited
projects too. A visible placeholder/sparse-scene blocker selects the next art batch; do not
merely append another criticism while adding quests or packaging another release. Complete
the arrival/player/companion/dialogue/battle sample before expanding content. Necessary
engine or input repairs remain allowed; user-deferred execution remains deferred. Maintain
observations and next fixes in the existing plan's ART item, with a concise status in the
Brief. You judge the actual images and play experience; passing pixel/geometry helpers
or writing a report is insufficient. No extra runtime gate or structured review file is needed.

## Project shape

Before multi-step implementation, read [the game planning guide](references/planning.md).
Use the shared index.md/plan.md contract at the exact plan-context paths. This skill guides
what a game needs to record; you choose the additional documents and directory structure.
Start small, split records only when useful, and adapt an inherited layout rather than
creating duplicate records to match an example. Respect explicit planning-mode overrides.
The runtime reads only index.md, never updates it automatically and never requires a
rewrite every few steps. Update affected records and the index after meaningful progress.

Use Godot 4 + typed GDScript. Native delivery is primary and Web export is optional.
For shared Web/native 3D content, start with Compatibility
rendering, restrained geometry/materials, baked/simple lighting, few shadowed lights
and readable silhouettes. Record exact engine/template versions. Prefer glTF/GLB for
interchange; runtime hosts should not need Blender merely to import a .blend file.
Keep asset sources, licenses and attribution in a ledger. Carry unresolved placeholder
replacement and visual-review items in index.md until addressed.

Suggested responsibilities (adapt rather than blindly generating empty directories):

```
game/project.godot
game/export_presets.cfg
game/scenes/{world,actors,battle,ui}/
game/scripts/{world,combat,quests,persistence}/
game/data/{creatures,moves,encounters,quests,dialogue}/
game/assets/
builds/<revision>/{web,desktop}/
reports/{campaign_ledger,play_journal,evolution}/
```

Use Resources or versioned JSON with stable IDs. Separate combat rules from rendering,
quest conditions from dialogue, and save data from live Node references. Seed random
choices, keep migrations explicit and write saves atomically with a recoverable backup.
Store full creature/party/quest/choice/world state needed to resume, not just a level.
Do not overwrite an unreadable or future-version save on failure. Provide manual slots,
accessible recovery and, if Web is delivered, save export/import. Verify persistence
on the actual delivery target; one platform's results cannot certify another.

## Genuine 3D play and native controls

Implement a third-person camera with occlusion handling, ground/collision checks,
readable interactable ranges and a stuck recovery. Include click-to-move, visible
interaction hints and pause/turn-based decisions alongside WASD. This is a usable
player control option for native gameplay input.

Use godot_environment for imports, per-script checks, bounded headless scenarios and
exports. Preserve logs. --check-only is one-file parsing; --quit-after counts engine
iterations. An assertion runner needs its own completion marker/nonzero failure exit.
Run only checks justified by the change and explicit user authorization.

Launch the shared project with godot_environment start_game and inspect its actual
observe/press_key/press_keys/move_mouse/click/type_text/input_sequence action schemas. Use a
rendered frame and ordinary player input, with bounded held keys and guaranteed
release. Observe the resulting position instead of inferring movement from elapsed
input time. Stop the game before imports, CLI checks or exports; import/restart after
edits so the played revision is known. inspect_runtime supplies tree/ui/logs/errors.

Use input_sequence for simultaneous keys and mouse, GUI shortcuts (key_tap modifier
flags), dragging, scrolling, double-clicks, captured-camera motion, gamepad buttons/axes
and touch gestures. Focus text controls by clicking before type_text. Test only device
types and bindings the game supports; verify visible results rather than input receipts.
Sequences release held inputs by default. For a hold across observations, set
release_at_end=false and explicitly release_inputs before the idle lease expires
(10 seconds by default); observation does not renew it. Use input_state to diagnose
stuck controls. Sequence limits are 32 steps, 10 seconds of explicit waits and a
15-second total deadline. Do not treat automatic idle release as an intentional move.
Keep real-player inputs separate from scene/UI/log inspection. Engine screenshots
do not verify sound, host-native dialogs or physical controller feedback.

Never substitute teleport/set_quest_state or other hidden-state edits for a real
player journey. Explicit debug harnesses may supplement visual evidence, and must
identify how they differ. Missing runtime control, startup failure or blank rendering
remains a blocker. Native checks cannot certify optional Web delivery. For exports,
use a fresh revision directory and verify the installed engine's actual preset syntax.

## Creative self-review

Before reading implementation details, play a concrete visitor goal from the current
screen and record what was visible, chosen, surprising and confusing. Tie the next idea
to an observed opportunity. A good idea changes the decisions available to the player:
for example, a companion recalls an earlier habitat rescue and opens a different route,
or a terrain ability changes both traversal and a later battle. Define a faithful small
trial rather than a decorative label. Alternate player observation and developer diagnosis;
keep these phases distinguishable. Self-play is not independent audience validation.

For each important loop, compare input/seed/save and visible results before/after. Track
decision variety, clarity, time to first meaningful choice and pacing alongside correctness.
Do not force target playtime using repeated battles, slow walking, timers or dialogue walls.

## Reusable agent capability gaps

Game content is the product; production/observation/analysis methods are potential agent
capabilities. Inspect existing capabilities and probe the specific unmet operation first.
Useful investigations include quest-state reachability, save migration verification,
reproducible 3D input traces, and battle/biome analysis. These are hypotheses, not mandatory
new modules. Compare a justified candidate against the same preserved baseline and a
different case before keep. Use the exact kept version in later real work and record_use
when the task requires it. A game-specific debug script becomes a reusable capability
only after generalization, registration, evaluation and actual adoption evidence.

Follow self_evolving_skill and the current adoption_tool schema. If no genuine improvement
can be established, leave that outcome unmet rather than fabricating evidence.
