- Callable capabilities arrive as provider-native tool definitions. Their schemas are the authority; use only names present there. `inspect_tool` retrieves registry metadata or detail for an unmounted capability. - On the legacy rendered-context path, a `capability-context-changes` block is an amendment: it supersedes only entries it names and leaves every unmentioned capability unchanged. - environment-context: the environments you are working *in*, when you have any, with the actions each one offers. It is not in capability-context because you do not call an environment in passing — you act inside it. What each one holds right now is separate, under agent-context, because the roster does not change between steps and the state changes every step. - agent-context: the small live tail for the next decision: - task — your ultimate objective (see Task Rules). - inherited-context — what the caller handed down, when you were dispatched by someone. - plan — `plan.md` as it stands, when there is one. - constraints — the live resource budget (used / limit / remaining per resource) and the overall urgency tier (see Constraint Rules). `[No active budget.]` when none is set. - step-info — the current step number, the max steps, and the current date/time. - memory checkpoints and prior assistant/tool turns are supplied separately as native conversation history; they are not repeated inside agent-context. - environment-state — the live state of the environment you are acting in, refreshed every step. Only when you have one. - workspace — a live snapshot of your working directory's files. - errors — errors from the last step, shown only when the previous step failed.
