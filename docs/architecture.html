🧬 AgentEvolver · Runtime & Agent Architecture

One loop. Many actors.
Typed channels between them.

Every agent — a leaf actor or an orchestrator — runs the same event-driven loop on an actor runtime, and talks to other agents over typed protocol channels. Orchestration isn't a special agent; it's a roster plus two seams.

The stack

Three layers — mechanism below, meaning above

Bottom to top: the runtime moves messages, the protocol layer gives each conversation a shape, and agents/tools speak those conversations. Each layer only knows the one beneath it.

The one loop

Every agent runs the same event-driven turn loop

There is no separate "meta runtime". MetaAgent is a normal Agent; it dispatches a sub-agent the same way a leaf agent calls bash_tool — a sub-agent is just another capability.

1

on_start(task, ref)

Runtime pump delivers the task; init the run, emit ON_START hooks, kick the first turn.

2

_advance() · one turn

Constraint check → _get_messages → _think → _prepare_round → _dispatch_round.

3

_think(messages)

One LLM turn → a batch of native tool_calls + a routing table.

4

_dispatch_round() · the round

Every call in this turn's batch runs concurrently as a background task; each posts an _ActionDone to this agent's own inbox. A sub-agent call = protocol.delegate.

5

on_event() → round drains

Collect finished actions; escalations are handled the instant they arrive.

6

↺ _advance (next turn) — or _conclude

_conclude: cancel stragglers, ON_STOP hooks, _finalize_run, resolve the caller, on_end.

round == turn

The calls the model emits in one turn are parallel-safe by the function-calling contract — so the whole batch runs concurrently. Dependent work is emitted across turns.

1 turn=1 concurrent round
__call__→runtime.invoke(self)

The synchronous entry point runs the exact same event-driven loop under a pump — direct call or dispatched sub-agent, one code path.

Native tool use

Each manager projects its own capabilities

The model sees one flat tools list. Every manager owns its own projection; assemble_native_tools only concatenates them and builds the routing table. Names are the entities' own registered names — already type-marked by suffix, never re-prefixed.

managers · function_callings()

  • tool_manager → done_tool, bash_tool…
  • skill_manager → *_skill
  • connector_manager → conn__action
  • agent_manager → *_agent (orchestrators)

assemble_native_tools

  • concatenate (schema, route) pairs
  • build the routing table
  • no renaming — raw suffix-marked names

_think → model → _run_one

  • model emits tool_calls
  • routing → owning manager
  • done_tool = completion
Escalation, end-to-end

A blocked sub-agent asks its parent — and resumes on the reply

The reference flow across all three layers. Because every agent runs the event-driven loop, the parent handles the escalation on its pump while the round is still in flight — no deadlock.

■ agent / tool ■ protocol channel ■ runtime transport
sub-agenthits a blocker it can't resolve alone
escalate_toolthe LLM's trigger — escalate(reason, situation, suggestion)
protocol.escalatepost an EscalationMessage to the parent's inbox
runtime.suspendthe sub-agent's coroutine parks on its task_id — its round stays open
parent · on_event_handle_extra_event → a focused think turn decides the guidance
protocol.replyreply(task_id, guidance) — via the parent's reply_tool / loop
runtime.resumeresolve task_id → the sub-agent wakes, returns the guidance, continues

Lineage: AgentContext.parent_session_id is what lets escalate find the parent — BaseContext.from_context preserves it through the AgentContext → ToolContext conversion so a tool can still see who dispatched it.

Model providers

Four providers, one model_manager contract

Each provider implements _build_params → _call_model / _open_stream → _parse_stream / _format_response. Structured output is derived: no tools → native schema; with tools → a synthetic tool folded back into parsed_model.
